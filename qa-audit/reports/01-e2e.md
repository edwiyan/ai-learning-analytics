## Test Infrastructure Note (Not App Bugs)

14 tests failed with `Login failed for <role>: 429`. Root cause: the `/auth/login` endpoint has a `@limiter.limit("10/minute")` rate limiter (auth.py:16), and 2 parallel Playwright workers hammered it with 57 back-to-back login calls. This is **not an app bug** — but it directly exposed a real P2 finding (see #2 below). Every test that reached retry after the rate window cleared passed cleanly. Security tests that failed due to 429 were re-verified via direct API calls with manually obtained tokens.

## Defects Found

### DEF-01 — P1: All `/analytics/me/*` endpoints lack explicit role guards
**Area:** Backend — `backend/routers/analytics.py`  
**Repro:** Call any `/analytics/me/*` endpoint with a PD, Dean, VP, instructor, or admin JWT.  
**Evidence:**
```
PD  → GET /analytics/me/risk?course_id=...  → HTTP 400 {"detail":"No student number on file"}
VP  → GET /analytics/me/risk?course_id=...  → HTTP 400 {"detail":"No student number on file"}
```
**Expected:** HTTP 403 Forbidden (role check runs before business logic).  
**Actual:** HTTP 400 with an implementation-detail leak ("No student number on file").  
**All 9 affected endpoints:**
- /me/courses
- /me/risk
- /me/competency-scores
- /me/trend
- /me/recommendations
- /me/interventions
- /me/attendance
- /me/consultations
- /me/academic-standing

**Risk:** If any non-student account ever has `student_number` set (admin misconfiguration, bulk import error), they silently gain access to student-grade personal analytics. Proper 403 before business logic is the correct guard.  
**Fix area:** Add `Depends(require_role(UserRole.student))` to each `/me/*` endpoint in analytics.py.

---

### DEF-02 — P2: Login rate limiter (10/min) too aggressive for institutional shared-IP use
**Area:** Backend — `backend/routers/auth.py:16`  
**Evidence:** `@limiter.limit("10/minute")` on the login endpoint. With 2 Playwright workers, 57 test login calls exhausted the limit in under a minute.  
**Real-world risk:** Multiple students/instructors logging in simultaneously from a computer lab (single external IP) will hit 429 errors. During a defense panel, if evaluators all log in at once, some will be blocked.  
**Fix area:** Raise limit to `30/minute` or `60/minute`, or exempt campus IP ranges.

---

### DEF-03 — P2: Vite dev proxy missing `/surveys` and `/attendance` routes
**Area:** `frontend/vite.config.js`  
**Evidence:** `vite.config.js` proxy block includes 14 route prefixes but is missing `/surveys` and `/attendance`. In development (`npm run dev`), API calls to these paths hit the Vite server and get 404.  
**Affected pages:** `SusSurveyPage.jsx` (cannot submit SUS responses in dev), `AttendancePage.jsx` (cannot load or save attendance in dev).  
**Evidence:** SUS survey test failed on retry after 429 cleared — page loaded but API calls silently failed. Attendance test 429 failure masks this.  
**Note:** Production Docker/nginx likely proxies correctly via nginx config, so this may be dev-only. But defense will likely run in dev mode.  
**Fix area:** Add `'/surveys': BACKEND, '/attendance': BACKEND` to `frontend/vite.config.js` proxy block.

---

### DEF-04 — P3: Wrong-password error message not visible on login page
**Area:** `frontend/src/pages/Login.jsx`  
**Evidence:** Admin wrong-password test passed (`body.match(/incorrect|invalid|unauthorized|error|wrong/i)` returned truthy) BUT the match was on a generic word in the page source, not a user-visible error message. Manual verification needed to confirm the error is prominently displayed to the user.  
**Severity:** P3 until manually confirmed.
